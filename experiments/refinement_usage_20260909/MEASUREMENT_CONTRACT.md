# Refinement measurement contract

Each evaluated method version must report dataset/model/revisions, canonical question count, F1 and its scorer, the exact answer-file path/SHA256, LLM tokens (M), embedding tokens (M), and clearly defined seconds per question. M is 1,000,000 tokens. Source-only inner-round fitness is not benchmark F1. Historical Qwen3-8B development is separate from current Qwen3.5-9B validation.

## Existing measured evidence

Completed Qwen3.5-9B + MiniLM runs: qwen35_baseline (Seed, r40, Refined) and recursive_v1. Inputs in evidence/ were copied from immutable completed runs, with a full file inventory and before/after remote hashes. INBOUND_VERIFICATION.json records local extraction and every input hash. The standalone local aggregator does not change experimental code, memories, models, caches or predictions.

Count only actual native generation and embedding calls once per invocation identity. Prompt plus completion tokens include scoring requests and generated scoring tokens. Identical requests in real retries remain separate cost; cached final answers have logical reader tokens but may consume no new model call. Token counts are not a measurement of uncached GPU FLOPs or monetary billing. Embedding counts are native post-256, nonpadding attention-mask tokens, including known failed forward attempts; padding is reported separately. Missing records or unknown failure consumption make totals incomplete, with known lower bounds preserved.

Report native cost by run and stage. Baseline preparation is shared execution across the starting methods. Utility scoring is ancestor work for Refined and recursive descendants; it is not a necessary standalone Seed/r40 cost. The existing building_seed context mixes Seed and r40 construction, so do not invent exact per-method allocation. Recursive construction is incremental work; it must not be presented as the total cost of constructing its inherited memory from scratch. Keep evaluation usage separate from construction and shared ancestor costs.

## Time definition and current limitation

For already completed runs, native inference seconds per question is the sum of leaf native LLM and embedding inference durations in the evaluation stage divided by the canonical question count. This is an amortized inference-service measure under the recorded batching/cache state. It excludes retrieval, packing, file writes, model initialization and other Python work, and is not individual user request latency. Never add nested operation/encode_attempt times to native call times. Never average generation_batch_seconds across answer rows: it repeats a conversation-level cumulative interval after retrieval.

End-to-end evaluation seconds per question was not recorded in the existing artifacts and remains null. Raw vLLM request metrics inspected so far are null; a complete receipt audit must report metric coverage. File mtimes, process ages and log spans do not substitute for this measurement.

The next-run timer is now implemented and independently reviewed locally in evaluation_timing.py and timed_evaluate.py. It starts perf_counter_ns immediately before the original evaluate_sample call and stops immediately after return or exception. Its scope includes document/query embedding, retrieval, ranking, packing, generation, existing native telemetry I/O, token accounting and row assembly/F1 inside that function. It excludes model initialization, outer item-cache checks, caller prediction-file persistence, and timing-sidecar I/O. The precise label is **evaluation-function wall time, amortized seconds per question**, not total-process E2E or individual request latency. Sum nonoverlapping evaluation-call intervals and divide by the corresponding canonical question count; native inference time remains a separate column.

The explicit launcher preserves original arguments and successful returned row objects. Each process session and each call receives a fresh UUID directory under the original output directory's evaluation_timing/ subdirectory. The recorder writes started.json followed by a distinct completed.json or error.json, binding the terminal receipt to the started-file SHA256. Completion records include IDs, count, elapsed seconds and the canonical in-memory returned-rows SHA256. Metadata pins the runner, evaluator file, actual evaluator function source, launcher and recorder. This canonical row digest is not the persisted prediction file's byte hash. Original evaluator exceptions are re-raised; a secondary logging failure adds only its type as a diagnostic note. Start/completion logging failures fail closed and can stop the call or prevent returning completed rows to the caller.

An outer item-cache hit can skip evaluate_sample entirely. Zero calls therefore means no measured evaluation, not zero seconds per question. An interrupted or failed attempt stays separate, and resumption creates new attempt identities. Previously completed artifacts cannot acquire historical wall times by being resumed. Any reporting code must identify missing coverage and overlapping attempts explicitly rather than average duplicate question IDs or treat unmeasured work as zero. Native receipt accounting stays active alongside timing.

The four Python addon files passed 19 CPU tests and independent Python review, including an actual Windows spawn child that does not duplicate evaluation. No real next-run wall-time measurements exist yet. timed_launch_preview/run_recursive_v2_queue.sh changes only the evaluate branch to call this launcher and verify its checksum; construction, predecessor, GPU-idle, disk and existing source checks are preserved. The source owner's original eight prepared files remain untouched. V2_TIMED_TRANSFER_CONTENTS.json is a LOCAL-only concrete 13-file, 79,212-byte proposed bundle. It expands the earlier rejected eight-file transfer scope and has not been approved or deployed. The final owner must freeze the timing-enabled queue's actual bytes in recursive_v2_source.sha256 after any explicitly authorized deployment. No alternate upload or remote execution has bypassed the pending approval.

## Local timing reporting

aggregate_evaluation_timing.py consumes one exact method's original final answer JSONL plus a collected timing-sidecar root. It emits EVALUATION_TIMING.json and .md in a new output directory. The mean is successful attributable evaluation-function seconds per question for the supplied population, requiring complete and unambiguous receipt coverage. Observed successful/failed attempts are separate costs; incomplete or contradictory records do not become zero. The reporter validates metadata and hashes but does not certify full benchmark coverage or actual model weights by itself.

The reporter passed 19 focused CPU tests and independent review. Together with the separately reviewed 19 timer/launcher tests, there are 38 timing-related CPU tests. Actual v1's 1,540 original answers with no timing receipts returned a null mean, as recorded in TIMING_INTEGRATION_CHECK.json. No real new evaluation-function timing exists yet. The local reporting files are not part of the proposed external transfer.
